# 骑行记录与分析 App 设计文档

日期：2026-09-21
状态：待用户审阅

## 1. 背景与目标

一个**个人自用**的骑行记录与分析 App。核心价值是把一次骑行完整、准确地记下来，并在事后回答两个问题：

- 这次骑得怎么样？（单次详情）
- 我最近骑得怎么样？（长期趋势）

不是社交产品，不是导航工具，不是训练平台。

## 2. 范围

### 做

- 骑行记录：手机 GPS 轨迹 + 蓝牙心率 + 蓝牙踏频 + 蓝牙功率计（可选，没接则按速度与坡度估算功率）
- 骑行中实时显示核心指标与实时轨迹缩略图
- 单次骑行分析：基础统计、心率分析、踏频分析
- 长期分析：周/月/年累计、趋势、个人最佳
- 地图轨迹展示，轨迹与速度曲线按速度着色
- 数据导出：单次 GPX 导出、全量备份与恢复

### 明确不做

以下为范围边界，用于防止后期蔓延。若需新增，应作为独立迭代重新评估。

- 账号体系、云同步、多设备同步
- 社交、好友、排行榜、路段
- 导航与路线规划、GPX 路线导入
- 室内骑行台
- Apple Health / 华为运动健康集成
- 多语言（仅中文）
- 自动运动类型识别

## 3. 关键决策记录

| 决策点 | 结论 | 理由 |
| --- | --- | --- |
| 用户范围 | 个人自用，数据纯本地 | 无账号无服务端，架构最简，无隐私顾虑 |
| 技术栈 | Flutter | 一套代码覆盖 iOS + Android，本机 fvm 3.47.4 已就绪 |
| 心率来源 | 华为 Fit 3 心率广播 | 官方兼容性清单确认三端支持，可当标准蓝牙心率带使用，零额外硬件成本 |
| 华为 SDK | 不接入 Health Service Kit | 申请需人工审核约 15 个工作日、限中国大陆、测试期限前 100 用户，个人项目不划算 |
| 记录引擎 | 方案 B：纯 Flutter + 增量落盘 | 用极小代价获得接近原生后台服务的可靠性，无需编写平台代码 |
| 地图 | `flutter_map` + 高德栅格瓦片 | 无需申请 Key、纯 Dart 实现、逐段着色轨迹支持最直接 |
| 速度着色范围 | 速度曲线 + 地图轨迹 | 两个视图共用同一套颜色映射，可互相印证 |
| 卡路里 | 做，简单估算 | 用体重 + 心率 + 时长估算，界面标注为参考值 |
| 记录界面 | 车把与口袋合并为唯一界面，记录 tab 落地即该界面；亮屏常亮，熄屏靠电源键 | 两种模式差的只是「常亮 + 读数极简」，而省电交给系统熄屏更彻底；留两套界面等于两套布局都要维护、都要为窄屏让预算。准备页同理只做三件事，传感器配对与开始键都在骑行界面上有更顺的位置 |

## 5. 架构与目录结构

分层原则：**`domain/` 是纯逻辑层，不依赖 IO，可脱离 Flutter 单独测试**。这是整个设计可测试性的根基。

```text
lib/
  app/          应用外壳：路由、主题、依赖装配
  features/
    record/     记录页与会话控制
    history/    骑行列表
    detail/     详情页（地图轨迹 + 曲线图）
    stats/      长期统计与趋势
    settings/   设置、传感器配对、导出备份
  domain/       纯逻辑，无 IO 依赖
    models/     Ride, TrackPoint, SensorSample, RideSummary
    analysis/   指标计算、心率区间、速度→颜色映射、趋势聚合
  data/
    db/         SQLite 打开、迁移、DAO
    ble/        心率与踏频订阅
    location/   定位采集
    export/     GPX 生成、备份打包
  core/         单位换算、格式化、日志
```

## 6. 记录引擎

### 6.1 状态机

```text
idle → preparing → recording ⇄ paused → finishing → saved
                      ↓ 崩溃/被杀
                   启动时检测到未结束会话 → 恢复
```

- `preparing`：申请定位权限、连接心率广播与踏频器。
- **传感器连接失败不阻断开始记录**。对应曲线留空即可，不能因为手环没连上就不让骑车。
- `paused` 期间停止采样，不产生轨迹点。

### 6.2 数据流

```text
定位流 ──┐
心率流 ──┼→ RecordingSession（内存当前态）─┬→ 实时 UI（前台 1Hz 刷新）
踏频流 ──┘                                ├→ 实时轨迹缩略图（见 9.4）
                                          └→ 落盘队列 → SQLite
```

实时 UI 与缩略图走的是同一份内存态，但刷新口径不同：读数每拍都刷新，缩略图只在轨迹点
真的追加进去时才重画（见 9.4）。

**退到后台不再刷新界面**。后台时 Flutter 的帧回调会被系统节流，继续 `publish` 既是白做功，
也可能让整棵子树在不可见的情况下重建。后台只保留采集与落盘，界面留到回前台时补一次。

### 6.3 落盘策略

方案 B 的核心，四条规则：

1. **轨迹点过滤**：距上一点距离 ≥5m，**或**距上次写入时间 ≥2s，满足其一即写入。移动时由距离触发（约 1Hz），静止时由时间触发降频至 0.5Hz。
2. **传感器批量提交**：1Hz 采样，攒够 10 个点提交一个事务，兼顾可靠性与写入开销。
3. **会话标记**：`rides` 表中保留 `status` 为 `recording` 或 `paused` 的行。App 启动时扫描该状态，决定是否进入恢复流程。
4. **后台加密落盘**：退到后台后，1Hz 节拍上不再每拍都提交，改为间隔 ≥3s 强制冲刷一次未提交的点。系统在后台对进程的调度会被拉长甚至冻结，1Hz 的节拍本来就不可靠；把冲刷从「每拍」改成「按时间兜底」，即使只在被唤醒的那几拍里跑，数据也照样落得下去。回前台时立即补一次冲刷。

### 6.4 崩溃恢复

启动时若发现未结束的骑行，提示用户：「检测到未结束的骑行，是否继续？」

- 选择继续：续写该会话。
- 选择结算：调用分析引擎算出汇总指标，将状态置为 `finished`，作为一条完整记录保存。

## 7. 数据模型

三张表，保持简单。

### rides

一次骑行一行。汇总指标**冗余存储**，使列表页与统计页无需每次重算。

```sql
CREATE TABLE rides (
  id                   INTEGER PRIMARY KEY AUTOINCREMENT,
  started_at           INTEGER NOT NULL,   -- epoch ms
  ended_at             INTEGER,            -- NULL 表示进行中
  status               TEXT    NOT NULL,   -- 'recording' | 'paused' | 'finished'
  title                TEXT,
  distance_m           REAL,
  duration_s           INTEGER,            -- 总时长
  moving_s             INTEGER,            -- 移动时长
  avg_speed_mps        REAL,               -- 总均速
  moving_avg_speed_mps REAL,               -- 移动均速
  max_speed_mps        REAL,
  elevation_gain_m     REAL,
  avg_hr               REAL,
  max_hr               INTEGER,
  avg_cadence          REAL,
  calories             REAL,
  hr_device_name       TEXT,               -- 本次心率来源设备名
  cadence_device_name  TEXT,
  point_count          INTEGER
);
```

### track_points

轨迹点与传感器采样**合并成一张宽表**。

这是本节最关键的取舍：合并后时间天然对齐、绘图只需单表顺序扫描、写入一次完成。代价是 GPS 丢失时（隧道、桥下）心率数据没有坐标——因此 `lat` / `lon` 允许为空，这类点照常绘制曲线，只是不画到地图上。

GPS 1Hz、心率约 1Hz、踏频 1Hz，频率一致，合并不会产生对齐冲突。

```sql
CREATE TABLE track_points (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  ride_id    INTEGER NOT NULL REFERENCES rides(id) ON DELETE CASCADE,
  t_ms       INTEGER NOT NULL,   -- epoch ms
  lat        REAL,               -- 可空：GPS 丢失时仍记录传感器数据
  lon        REAL,
  altitude_m REAL,
  speed_mps  REAL,
  accuracy_m REAL,
  hr         INTEGER,
  cadence    INTEGER
);
CREATE INDEX idx_track_points_ride_t ON track_points(ride_id, t_ms);
```

### settings

```sql
CREATE TABLE settings (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
```

存放最大心率、体重、单位、地图瓦片源等配置。

## 8. 分析引擎

全部为**纯函数**，放在 `domain/analysis/`，不依赖 Flutter 与 IO。

### 8.1 必须处理的数值陷阱

这三个问题不处理，算出来的数字会假得离谱：

1. **爬升**：原始高程噪声会把 100m 的爬升算成 800m。处理方式：对高程做窗口为 5 点的中值滤波（`kElevationFilterWindow`），再只累加单次上升超过 1m 的区段（`kElevationGainThresholdM`）。滤波窗口与阈值作为具名常量定义在 `domain/analysis`，便于调整和测试。
2. **最高速**：GPS 瞬时速度毛刺严重，直接取最大值会得到「最高时速 78km/h」这类无效数据。处理方式：对速度做窗口为 5 点的滑动平均（`kSpeedFilterWindow`）后再取峰值。
3. **曲线锯齿**：画到图上的曲线是另一回事。上面两条只管「读数值」，曲线要读的是趋势，残余噪声会直接变成看得见的锯齿——真机上「曲线不圆润」看到的其实就是噪声，不是骑行节奏。处理方式是给曲线单独一套更长的平滑窗口：

| 曲线 | 平滑窗口 | 常量 | 说明 |
| --- | --- | --- | --- |
| 速度曲线 | 31 点 | `kSpeedCurveFilterWindow` | 2 秒一个采样点时约 62 秒；GPS 速度噪声 σ≈0.26 m/s，5 点窗口后仍有 0.12 m/s，映射到 140px 高的图上是两三个像素的细齿 |
| 心率 / 踏频 / 功率曲线 | 21 点 | `kSensorCurveFilterWindow` | 约 42 秒，足以摊平传感器逐点抖动；这三项的真实变化本就是分钟级，不会被抹掉 |

**读数与曲线的窗口口径不同，不要混用**：`kSpeedFilterWindow = 5` 只给最高速读数，`kSpeedCurveFilterWindow = 31` 只给速度曲线。曲线上的极值标注也因此取自画出来的曲线，而不是汇总读数（见 10.3）。

平滑**不填补空缺**：踏频器骑到一半才连上时，前半段不会凭空长出一条踏频曲线。

**实时海拔与累计爬升（骑行中读数）与结算同一条口径**。骑行界面上的「海拔 / 爬升」两格
（见 10.1）不能等结束时才算，但口径必须和 8.3 的结算值对得上，否则同一趟骑行在结算前后
会给出两个爬升数。做法是把「剔除不可信高程点 → 中值滤波 → 滞回累加」封成一个入口
`elevationGainOf(points)`，汇总与崩溃恢复都走它；实时读数用同一套滞回循环，只省掉中值滤波
（滤波窗口要取当前点之后的样点，实时拿不到未来）。

**滞回是与「基准」比，不是与上一个点比**。缓坡每步只升 0.6 米，逐步比较永远够不到 1 米的
阈值，几十公里的爬坡会被整段丢掉。基准只在两种情况下推进：单次上升 ≥ 阈值（记增益并前移），
或单次下降 ≥ 阈值（只前移，不记增益）。

**高程突变按坡度判定，不设绝对上限**。隧道、桥下之后的海拔突变是真实的：那里水平位移大，
按坡度算下来完全正常，不该被当成异常吃掉。判定条件是「变化 ≥ `kSuspectElevationJumpM`
**且** 坡度 > `kMaxPlausibleGrade`」；没有坐标的点（GPS 丢失期间）按「没动」处理。

### 8.2 指标定义

- **总均速**：总距离 / 总时长。
- **移动均速**：总距离 / 移动时长。移动与静止基于速度阈值判定，阈值取 1 km/h：低于该速度的时间计入静止。等红灯的时间不应拉低均速。
- **心率区间**：按最大心率的百分比切分为五区，输出各区间时长与占比。最大心率由用户在设置中配置。
  - Z1 <60%（恢复）
  - Z2 60–70%（耐力）
  - Z3 70–80%（节奏）
  - Z4 80–90%（阈值）
  - Z5 >90%（无氧）
- **卡路里**：基于体重、心率、时长的估算公式。UI 上标注为参考值，不作为精确指标。
- **估算功率**：没接功率计时，由速度、坡度与体重按三项阻力模型估算轮上功率：

  ```text
  P = v · ( m·g·Crr + ½·ρ·CdA·v² + m·g·grade )
  ```

  三项分别是滚阻、风阻与坡阻（`analysis/power.dart`）。**坡度用最小二乘拟合而不是两点相减**——高程在秒级尺度上噪声有几米，而 30 秒里真实的爬升可能不到两米，两端相减量的基本是噪声。下坡逆推出来的负功率按 0 处理。

  算出来的是轮上功率，没算传动损耗，系统性偏低几个百分点；本来就是估算，不再乘传动效率去假装精确。**存进 `track_points.power_w` 的数值与实测功率同形**，靠 `rides.power_device_name` 是否为空来区分，界面据此在标题里标「（估算）」（见 10.3）。接了功率计时走的还是同一列，界面不标。
- **速度 → 颜色映射**：归一化色带，速度越快颜色越深。同一函数同时用于速度曲线与地图轨迹着色，保证两个视图视觉一致。

### 8.3 计算时机

骑行结束时调用一次 `computeSummary(points)`，结果写入 `rides` 的汇总字段。列表页与统计页直接读冗余字段，不重算。

## 9. 地图与轨迹渲染

### 9.1 实现路径

使用 `flutter_map` + 高德栅格瓦片。

- 优点：无需申请 Key、纯 Dart 实现、`PolylineLayer` 对逐段着色支持最直接。
- 风险：走的是非官方瓦片接口，属于灰色地带，接口变更会失效。
- **对冲措施**：瓦片源地址作为 `settings` 中的可配置项。接口失效时用户可切换到 OSM 或自建源，无需改代码重新发版。

### 9.2 轨迹着色

轨迹按相邻两点的平均速度分段着色，复用 8.2 中的速度→颜色映射函数。

### 9.3 GPS 断点处理

相邻轨迹点时间间隔超过 10 秒时，判定为信号丢失，**不连线**。否则会在地图上画出一条横穿隧道或建筑物的假直线。断点两侧的线段各自独立着色，不影响速度着色的连续性。

### 9.4 实时轨迹（骑行界面全屏地图）

骑行界面**整页铺的就是这张实时地图**，读数与按钮以半透明浮层压在上面（见 10.1），
复用 9.2 的逐段着色与 9.3 的断点规则，瓦片源同样跟着 `settings` 走（见 9.1）。
它与详情页地图有三处刻意的不同：

**抽稀口径放宽**。落盘那套（6.3）要求忠实，`RecordingSession` 里另存一条 `liveTrack` 只求形状：
距上一点 ≥25m **或**间隔 ≥15s 才追加，上限 400 点，超过时折半压缩、保留最新点。地图铺满整页后
每像素对应的实际距离确实变小了，但轨迹只是底图，读数在浮层上；按落盘口径攒下的点画在这上面
分辨不出差别，白占内存和重绘时间。

**列表对象原位不换**。没有新点追加时不重建 `liveTrack` 实例，`didUpdateWidget` 靠 `identical`
就能判定「没变」直接返回——每拍都按新列表对象处理的话，等于每秒把同样的轨迹重画一次。

**相机只在必要时重新取景**。首次取景交给 `initialCameraFit`（它要等拿到尺寸才生效，`onMapReady`
比尺寸回调更早）；之后只有最新点跑出当前视野才重新 `fitCamera`。每来一个点就重新取景的话，
图会一直在缩放。

**没有定位点时是占位态**，显示「等待定位…」，此时不构建地图。室内无定位时能立刻看出是没数据，
而不是盯着一张空白底图等。占位文案**往上偏**（`Alignment(0, -0.45)`）而不是居中：居中会被
底部那块浮层压住，看不见。

地图不参与手势：`InteractiveFlag.none`，避免骑行中误触拖走视野。

**铺满与固定的两种用法**。`LiveRouteMap.height` 为 null 时铺满父约束（骑行界面），
给了值就固定高度（详情页等处）。浮层是半透明的，底图瓦片偏浅时白字会糊，因此地图上方
与下方各压一条渐变遮罩（`_Scrim`，从 `kAppBackground` 0.92 渐到全透明），保证压在上面的
文字始终有对比度。

## 10. 页面与交互

底部四个 tab：**记录 / 历史 / 统计 / 设置**。

### 10.1 记录页

**记录 tab 落地就是骑行界面**，没有独立的准备屏：进来看到的是完整的读数区（未开始态），
底部那颗整宽大键写「开始」，按下即开始记录，底部随即换成按频率分宽的两键动作区。

- 状态条：未开始 / 进行中 / 已暂停，加三个传感器灯（**不放任何动作键**）
- 主指标字号 ≥72pt，深色高对比，户外强光下可读
- 显示当前速度、距离、时长、海拔、爬升、心率、踏频、功率

**整页是地图，文案与按键悬浮其上**。骑行界面就是一块铺满的实时地图（9.4），读数与按钮
以半透明浮层压在它上面，分为上下两块：

| 位置 | 内容 |
| --- | --- |
| 顶部浮层 | 状态条 + 四格读数：**距离 · 时长 · 海拔 · 爬升** |
| 中间 | 提示横幅（见下方「骑行中的提示」），浮在地图可见带里 |
| 底部浮层 | 120pt 大速度 + 刻度尺 + 三格读数（心率 · 踏频 · 功率）+ 动作区 |

**读数为什么这样分块**。速度是骑行中唯一需要「扫一眼就看清」的量，独占底部浮层的上半部分，
用 120pt 仪器字体（`kInstrumentNumeralSize`），配一条刻度尺画出「现在有多快」的档位感；
其余六项按「整车视角 / 身体视角」分两组：距离、时长、海拔、爬升是这一趟的**整车状态**，
放顶部；心率、踏频、功率是**身体输出**，放底部贴着速度。两块浮层都是 `kAppSurface` 0.86
半透明 + 1px `kAppHairline` 描边，既不挡住地图，又保证读数有底。

**布局高度预算**。360×640dp 的机器上，底部 `NavigationBar` 占 64dp，正文区约 552dp；
顶部面板约 112dp、底部面板约 320dp，合计 432dp，留出约 120dp 的纯地图可见带。底部速度数字
外套一层 `FittedBox(scaleDown)`，窄屏或字体放大时不溢出（真机验收项）。

**提示横幅不参与布局**。它放在上下两块之间的 `Expanded` 里，用 `Stack` 对齐，出现与收起都
不挤压上下两块——否则每闪一次，读数与按钮就会跳一次，骑行中瞄一眼就是「界面在动」。

**底部动作区，未开始与记录中刻意不同**：

- 未开始：一颗整宽大键「开始」
- 记录中：「结束」占 1/3 靠左，「暂停 / 继续」占 2/3 靠右，两键隔 `kSpaceL`
- 屏幕常亮（wakelock），条件为「正在记录且未暂停且在前台」

**为什么不再有准备页**。原来那一屏只做三件事：连传感器、交代注意事项、给一个开始键。前两件
现在都有更好的位置——传感器配对在两个地方（顶部三盏灯、未连接的指标格），注意事项在骑行界面上
一句话说完就行。省掉一屏的实际收益是：进 tab 就能看见今天要用的界面长什么样，不用先点一次才能
确认布局对不对。

**底部动作区按频率分宽，不按语义分主次**。这是「位置合理化」真正要解决的问题。骑行中真正频繁
按的是「暂停 / 继续」——红灯、休息、拍照，一次骑行按十几次；「结束」一次骑行只按一次。所以宽
度该跟着频率走：主动作拿 2/3，落在右手拇指最容易够到的右下角；「结束」只占 1/3，被推到左侧。
破坏性动作靠三样东西兜底——更窄的宽度、一个 `kSpaceL` 的实体间隔、以及确认弹窗——而不是只靠
一颗键上那两个字。

由此未开始态与记录中态的底部布局是**不同**的，这是刻意的：未开始只有一件事可做，那颗「开始」
就整宽独占。代价是主键的位置在开始前后会变，换来的是「拇指不必在同一颗键上分辨两个含义相反的
动作」。中途改方向的教训是：曾经把「暂停 / 继续」降级到状态条右侧那颗 40dp 小键来保住单键换字，
结果最频繁的动作被放到了屏幕最难够到的顶部，而且紧挨三盏配对入口的传感器灯——误触会当场弹出
模态选设备面板，骑行中弹模态比按错键更糟。状态条现在不放任何动作键。

**没连上的指标可以就地重连**。心率 / 踏频 / 功率三格在未连接时值显示为 `--`，整格可点并带一个
「+」角标，点击弹出对应的选设备面板，与点顶部传感器灯等效。看到 `--` 最直接的动作就是点那一格，
不必先去找顶上那盏小灯。已连接的格子不给点击入口——读数正常时点它弹面板是纯粹的误触风险。
两种入口的提示文案刻意分开（灯是「点击连接心率设备」，格是「心率未连接，点击连接」），否则同一
屏上两个 tooltip 内容相同，测试和用户都无法分辨命中哪个。

**阻断类错误显示在这一屏上**。「开始」因定位权限或定位服务失败时，错误就贴在底部动作区上方：
不说清楚的话，一颗点了没反应的键比没有这颗键更糟。写入连续失败（11.2）也走同一个位置。

**骑行中的提示**。三类事件各提示一次，同时走**屏内横幅 + 语音播报**两条路：

| 事件 | 触发判据 | 常量 | 播报内容 |
| --- | --- | --- | --- |
| 整公里 | 累计距离每满 1km | `kCueLapM` | 该公里的均速与耗时 |
| 里程 | 累计距离每满 10km | `kCueDistanceTierM` | 累计里程 |
| 速度 | 速度向上跨过 10km/h 的整档 | `kCueSpeedTierKmh` | 跨档那一刻的实际速度 |

判据都落在 `domain/recording/cue_detector.dart`，是**纯逻辑**：挂在 `RecordingSession.tick()`
的 1Hz 节拍上，只在**跨过整档**时产出一次，因此同一公里、同一档位不会重复插话。

**速度档只升不降**。丘陵路段速度会在 20 档上下反复穿越，做成双向触发就会一路插话插到爆。
一次骑行内同一档位只播一次（`_speedTierKmh` 单调不减）；瞬时量没有「历史最高档」可落盘，
崩溃恢复时这一档从 0 重新起算。

**报实际速度，不报档位下沿**。这一条是真机验收当场改的：原实现报档位下沿，屏幕上出现
「速度 20.0 km/h」而同一时刻底部大数字是 25.9，同屏两个数对不上，用户只会以为哪里算错了。
触发判据（跨整档）不变，内容改成跨档那一拍的实际速度。

**崩溃恢复要播种基线**。`CueDetector` 支持按已落盘的距离与时长播种：不播种的话，续写一个
已经骑了 12 公里的会话，第一拍就会把 1~12 公里逐条补报一遍。整公里的耗时按「该公里的起止
时刻之差」算，暂停不计入。

**为什么必须带语音**。骑行中手机常常按下电源键熄屏、塞进口袋，此时屏内横幅根本看不见。
因此 `_drainCues` 的位置**刻意在「是否在前台」判断之前**：后台不重建界面状态（省 CPU），
但语音照常念。只在亮屏时播报等于这个功能没做。

**语音是尽力而为**。设备没装 TTS 引擎、语言包缺失、引擎被系统回收，都在
`TtsRideCuePlayer` 里静默跳过——屏内横幅照常提示，记录本身更不受影响。播报出口抽成
`RideCuePlayer` 接口，测试里换成假实现，既不出声也不依赖设备装没装中文语音包。

**横幅的显示时长是事件性的**。它到点自己收回（5 秒），不排队：两次提示挨得很近时，后一条
重置计时直接替换前一条——排队意味着屏幕上停着一句已经过时的话。

**熄屏与常亮**。亮屏就常亮，省电交给用户按电源键熄屏。息屏与切后台在代码里是同一个事件
（`AppLifecycleState` 离开 `resumed`），因此不新增任何 Android 平台代码：离开前台一律先关掉
常亮并在状态里标记前台标志，采集与落盘照常（见 6.2 / 6.3），回前台时补一次刷新。常亮除了跟随
生命周期通知，另加一道兜底——暂停中息屏、或通知还没送达，都必须在离开前台时立刻关掉，否则屏幕
会在黑屏状态下继续耗电。

### 10.2 历史页

卡片列表，按时间倒序。每张卡显示日期、距离、时长、均速、爬升，以及一条**着色的迷你速度曲线缩略图**——作为列表页的视觉锚点，便于一眼识别出强度较高的骑行。

### 10.3 详情页

自上而下：

1. 着色地图轨迹
2. 汇总指标网格
3. 速度曲线（着色）
4. 心率曲线 + 心率区间分布条
5. 踏频曲线
6. 功率曲线（没接功率计时标题写作「功率（估算）」，见 8.2）
7. 导出 GPX 按钮

**每项指标自成一组**：标题 → 该项读数 → 该项曲线。原来所有读数挤在顶部一张规格表里、所有曲线排在下面，读「心率多少、心率怎么变的」要在两处之间来回对；并到一组之后从上往下读一遍就够。

**曲线标注**（四条曲线一致）：

- **最高 / 最低**：在曲线自身的峰顶与谷底各打一个圆点，旁边写出数值。取自**画出来的曲线**而不是汇总读数——读数用 `kSpeedFilterWindow = 5`、曲线用 `kSpeedCurveFilterWindow = 31`，两者不是同一个数，标上去的点必须真的落在曲线上，否则标注本身成了误导（见 8.1）。曲线是平的（上下限重合）时只标最高点，两个标签叠在一起反而看不清。
- **平均**：一条横穿图表的虚线，右端写「平均 xx 单位」。取自**汇总读数**（`RideSummary`）而不是就地算曲线均值：屏幕上方就写着「平均心率 142」，参考线必须和它对得上，否则用户会以为哪里算错了。虚线用弱色，平均值是参考，不该和曲线抢注意力。

数值格式与上方读数同口径：速度一位小数，心率 / 踏频 / 功率取整。

### 10.4 统计页

周 / 月 / 年范围切换 → 累计距离、时长、爬升 → 趋势折线 → 个人最佳纪录卡片。

趋势折线的三个细节：

- **纵轴刻度**：步长取 1 / 2 / 5 序列，最多 4 条刻度；步长不足 1 时标签保留**一位小数**，否则相邻刻度会被四舍五入压成同一个整数。
- **横轴日期**：每个桶的日期都列出来（竖排），不再隔几个跳一个——跳过之后剩下的日期对不上自己关心的那天，等于没标。
- **触摸读数**：提示框里标出所属的日期桶，读数保留**两位小数**。默认样式直接把 `toString()` 印出来，小数位长到没法看。

### 10.5 设置页

最大心率、体重、单位、传感器配对管理、地图瓦片源、全量备份与恢复。

## 11. 错误处理

按「是否阻断骑行」分两类。

### 11.1 阻断类

不满足则不允许开始记录：

- 定位权限被拒 → 引导前往系统设置
- 定位服务关闭 → 提示开启

没有定位就没有骑行记录，这两项必须前置校验。

### 11.2 非阻断类

记录继续，界面如实反馈：

| 情况 | 处理 |
| --- | --- |
| GPS 信号弱或丢失 | 状态栏显示「信号弱」；轨迹在断点处不连线 |
| 心率广播未开启 | 给出针对性指引（手环设置 > 心率广播），而非笼统的「连接失败」 |
| 传感器中途断开 | 对应指标变灰；指数退避自动重连（1s→2s→4s，上限 30s） |
| SQLite 写入失败 | 重试；连续失败则提示用户 |
| 骑行中崩溃 | 启动时走恢复流程（见 6.4） |
| 备份恢复版本不匹配 | 执行迁移，或明确拒绝并说明原因 |

## 12. 数据导出与备份

- **单次导出 GPX**：从详情页触发，生成标准 GPX 1.1 文件，通过系统分享面板导出。心率与踏频写入 Garmin `TrackPointExtension` 扩展（`gpxtpx:hr`、`gpxtpx:cad`），确保 Strava、码表等平台能正确读取。
- **全量备份**：导出 ZIP 归档，内含：
  - `manifest.json` — schema 版本号、导出时间、记录条数
  - `rides.json` — 全部骑行记录
  - `track_points.jsonl` — 全部轨迹点，每行一个 JSON 对象（数据量大时流式读写，避免整份载入内存）
- **恢复**：选择归档文件导入，先校验 `manifest.json` 中的 schema 版本。版本一致则写入；版本较旧则执行迁移；版本较新则明确拒绝并说明原因，避免静默损坏数据。

## 13. 测试策略

按可测性分层，把测试力气集中在纯逻辑上。

- **`domain/analysis` 单元测试（重点）**：爬升滤波、最高速平滑、心率区间边界、Haversine 距离、移动/静止判定。这些逻辑出错会直接产生假数据，必须有测试兜住。
- **`data/db`**：使用 `sqflite_common_ffi` 开内存库测试 DAO，不依赖真实设备。
- **记录引擎**：注入假的定位流与传感器流，测试状态机转换、批量落盘、崩溃恢复。这是方案 B 可靠性的根基。
- **Widget 测试**：骑行界面的渲染与窄屏布局回归、未连接指标格的重连入口、缩略图的占位态与有轨迹态、详情页空数据态。
- **不自动化**：真实 BLE 硬件、真实 GPS、地图渲染。这三项手动验证，自动化性价比过低。

## 14. 真机验证结论与残余风险

### 14.1 验证方式与覆盖边界

验证在 **OPPO R9s Plus（Android 7.1.1，1080×1920，密度 480）** 上做，debug 构建经
`adb push` + `pm install -r -t` 装机（该机型走安装器会卡住，只能绕过）。心率源为华为 Fit 3。

**定位用的是系统模拟定位注入，不是真实户外骑行。** 这一条决定了本节的判据边界：
权限校验、落盘、断点判定、列表刷新这些管线层面的行为都被覆盖到了，而「轨迹贴合道路」
「隧道口不画假直线」这类依赖真实 GPS 抖动与真实遮挡的判据**不算已覆盖**——模拟定位给的
是理想轨迹，它能证明代码路径通，不能证明真实数据下好看。计划书 Plan A Task 22 与
Plan B Task 13 Step 7 里依赖户外的那几项因此仍挂着。

已记录到结论的项：Plan A Task 22 的 Step 1/2/3/5/6（全量测试、装机启动、阻断类校验、
落盘核对、崩溃恢复），Plan B Task 13 Step 7 的第 2 项（记一次骑行→历史出现卡片→详情页
各区块）、第 6 项（统计页三档切换）、第 10 项（瓦片源换源，见 14.3 缺陷 2）。

**最近一轮（全屏地图 + 实时海拔爬升 + 骑行提示）在同一台机器上做的**，注入 100000 步的
模拟轨迹跑完整流程，覆盖：整页地图与上下浮层在 360×640dp 下不溢出、四项读数（距离 / 时长 /
海拔 / 爬升）有值、功率估算有值、1.30 km 处整公里横幅出现且 5 秒后自动收回、横幅进出时
上下两块读数与按钮不跳动、速度跨档横幅出现、语音经系统 TTS 引擎经扬声器念出、结束结算走通。
**爬升读数为 0 是真实的**——模拟轨迹是等高程的，不是没算出来。用完仍留在 14.4。

### 14.2 已确认的结论

1. **Fit 3 心率广播是标准 BLE HRS** —— **已真机验证：可以**。最小 BLE 扫描程序确认能
   发现 `0x180D` 心率服务，按标准 HRS 订阅后读数正常（见 `lib/data/ble/ble_ids.dart`）。
   心率来源方案不变。
2. **记录引擎在真机上按 6.3 / 6.4 的预期工作**：轨迹点与传感器采样正常落盘；强杀进程后
   重开能弹出「检测到未结束的骑行」，继续与结算两条分支都正确。
3. **地图渲染、三条曲线、统计页周/月/年三档在真机上均能正常构建**。
4. **中文语音播报在 Android 7.1 上可用** —— 系统里装了讯飞与 ColorOS 两个语音引擎，
   `flutter_tts` 走通：`TTS: Utterance ID has started/completed` 成对出现，音频通路
   开到扬声器（`enable_snd_device: snd_device(2: speaker)`），整公里与速度提示都念了出来。

### 14.3 真机验证暴露并已修复的缺陷

六个都在真机上复现过，前三个是首轮验证的直接产物，第 4、5 个是后续复核时补上的，
第 6 个是全屏地图这一轮当场发现并当场改掉的。

| # | 现象 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | 结束骑行保存后切到历史页，列表还是旧的；杀进程重开才出现 | `historyRidesProvider` 等 4 个 `FutureProvider` 取过一次就缓存住，全项目没有任何地方让它失效 | 装配层引入 `RideDataRevision` 集中失效信号（`b02d9fd`） |
| 2 | 把瓦片源换成 OSM 后轨迹整体偏移约 310 m | `route_segments.dart` 无条件做 `wgs84ToGcj02`，而 OSM 本身就是 WGS-84，再转一次反而偏出去——等于 9.1 的对冲措施一上线就失效 | 坐标跟着瓦片源走，新增 `isGcj02TileSource()` 只按主机名判定（`507c59c`） |
| 3 | 统计页周视图 Y 轴印成 `0 / 1 / 1 / 2 / 2` | 没给 `SideTitles.interval`，`fl_chart` 自算 0.5 步长，而标签按 `round()` 格式化 | 显式给 1/2/5 序列步长，并把轴顶补到步长整数倍（`507c59c`） |
| 4 | 「爬升」被异常跳变污染，出现 500 m 假爬升 | 首个定位点常给出高程 `0`，次点才是真实海拔，两点水平只差几米却被整段算成爬升 | 新增 `plausibleElevationSeries`，跳变幅度够大且坡度物理上不成立时把相邻两点都置空（`a4717d8`） |
| 5 | 切到英里后趋势图标题与爬升单位仍写 km / m | 单位写死，只换了列表没换图表 | 新增 `formatElevation` / `distanceUnitLabel`，落地四处爬升显示（`a4717d8`） |
| 6 | 速度提示横幅写「速度 20.0 km/h」，而同一时刻底部大数字是 25.9 | `SpeedCue` 存的是跨过的**档位下沿**（20），文案却按「当前速度」来念，同屏两个数对不上 | `SpeedCue` 改存跨档那一刻的实际速度；触发判据（跨整档）不变 |

缺陷 2 的修复**没有做真机端到端复核**：默认高德源这条路径由 `detail_page_test.dart` 的
「高德源：轨迹转成 GCJ-02」覆盖（行为与修复前一致），而 OSM 侧在当时的网络环境下验不了。

### 14.4 仍未验证（残余风险）

1. **心率广播与华为运动健康的连接冲突**（原风险 2）。华为文档指出，仅支持单连接的穿戴
   设备（举例中包含 WATCH FIT 系列）开启心率广播后会断开与华为运动健康 App 的连接。
   本次未单独实测，不假定无此行为。
2. **真实户外 GPS 下的两项判据**：轨迹是否贴合道路（GCJ-02 转换在真数据下的效果）、
   隧道 / 桥下是否按 9.3 断开。模拟定位覆盖不到。
3. **OSM 换源的可用性**。本次尝试时 `tile.openstreetmap.org` 被 DNS 污染解析到
   `31.13.112.4`、100% 丢包，底图根本加载不出来，只能证明「换了源会走 WGS-84 分支」，
   不能证明「换个源就能用」。9.1 的对冲措施仍待真实可用的第三方源验证。
4. **真实 BLE 踏频器**：读数刷新、停转保持、断连后 1s→2s→4s 指数退避重连，均未实测。
5. **备份恢复**：`FilePicker` 拿到的 content URI 上 `readAsBytes()` 是否可用未实测
   （测试环境没有文件选择器与分享通道）。
6. **两种记录模式与功耗**：本条已随 10.1 的改动失效——界面合并后不存在模式切换。取而代之的
   待验证项见下一条。
7. **骑行界面全屏地图的真实瓦片渲染**（本轮更新）。合并那一轮室内无定位，地图停在
   「等待定位…」占位态；本轮用模拟定位注入拿到了定位点，**底图瓦片加载出来、橙色轨迹折线
   画在成都那条模拟轨迹上**，这两件事已从「只算代码路径通」升级为「看过」。仍未覆盖的是
   **真实户外 GPS 下的贴合度**：模拟定位给的是理想轨迹，瓦片与折线叠得准不准、
   「新点跑出视野时才重新取景」在真实抖动下会不会频繁触发，都还是模拟数据证明不了的。
   需户外一次完整骑行才能确认，与第 2 条同批。
8. **每 10 公里里程提示未真机验证**（新增）。按 25 km/h 要连续骑 24 分钟以上才能跨过
   10000 m，本轮只跑到 1.30 km，真机上没走完一档；整公里与速度跨档两类提示都已在真机
   看到横幅并听到语音，唯独这一类只经模拟定位跑不通时间尺度。判据本身由
   `cue_detector_test.dart` 覆盖（10000 / 15000 / 20000 m 三拍，跨档报一次、档内不重复、
   下一档接着报），文案由 `ride_cue_text.dart` 的单测覆盖，缺的只是真机那一嗓子。
9. **一次未能复现的异常结束**（新增）。真机验收中首次点击「心率」指标格，注入的 tap 让界面直接
   弹出「记录已保存」并结束了骑行；同一坐标随后重测两次均正常（一次无反应、一次正常弹出「选择
   心率设备」）。像素坐标核对无误（落在心率标签带内），也没找到能绕过确认弹窗直接 `finish()` 的
   路径，因此判定为一次未能复现的事件而非已确认缺陷。**记录在此备查**：若后续在真机再现，
   优先查注入事件与确认弹窗的时序。
10. **iOS 端**：全部未验证。
